# 对照评测设计：带 skill vs 不带 skill

> 本文件是 **A5 的执行规格**。目标维度：智能体与模型优化技术深度 25%。
> 官方原话：「这个评测必须包含负向用例，有些任务的正确答案就是不调用这个 Skill。」（刘春辉）
> 官方承认的痛点：「触发稳定性——Claude 常不主动触发」。本设计正是对该痛点的量化。

---

## 1. 实验组设计（四臂）

| 臂 | 配置 | 回答什么问题 |
|---|---|---|
| **A 基线** | 裸模型，**不加载任何 SKILL.md**，仅给同一份任务提示 | 下界。模型在没有领域知识时能做到什么程度 |
| **B 全量** | 加载完整 skill（含 `description` 的 `Not for...` 段 + 正文 + references） | **主实验组**。本项目实际交付形态 |
| **C 消融** | 加载同一 skill，但**从 `description` 删除 `Not for...` 段** | 负向条件到底值多少分 |
| **D 仅描述**（可选） | 只给 `description`，不给正文与 references | 分离「路由能力」与「知识能力」的贡献 |

**C 臂是本设计的关键**：它把「写 Not for」这一动作的收益单独隔离出来。
若 `FTR(B) ≪ FTR(C)`，即构成「负向条件显著降低误触发」的直接实验证据——
这正是官方承认的触发稳定性痛点的解法。

## 2. 控制变量（必须锁死，否则结论无效）

- 同一模型、同一版本、同一 `temperature`（建议 0）
- 同一 system prompt 模板，**仅 skill 加载部分不同**
- 同一组测试素材、同一用例顺序（含固定的随机种子）
- 每条用例重复 **≥3 次**（观测触发稳定性，取多数票并记录方差）
- 用例集合：`skills/*/evals/cases.jsonl` 共 **40 条**（正向 21 / 负向 16 / 空结论 3）

## 3. 指标表（A5 逐项填数）

| # | 指标 | 定义 | A 基线 | B 全量 | C 消融 | D 仅描述 |
|---|---|---|---|---|---|---|
| 1 | **负向误触发率 FTR** | 负例中**该用例 `skill` 字段所指技能**被错误调用的占比（本技能口径，见 `../README.md` §6）← **核心指标** | | | | |
| 2 | 负向正确拒绝率 | `1 − FTR` | | | | |
| 3 | 触发准确率 | `expect_trigger` 判定正确率 | | | | |
| 4 | 路由序列精确匹配率 | 编排层用例的路由序列完全正确率 | | | | |
| 5 | 结论正确率 | hazard_code 集合精确匹配率 | | | | |
| 6 | 读数 MAE | 指针表按满量程归一后的平均绝对误差 | | | | |
| 7 | **编造量程数** | 量程未知时仍给出数值的次数（应为 0） | | | | |
| 8 | **幻觉项数** | 报告中无法回溯到输入的条目数（应为 0） | | | | |
| 9 | 边界合规率 | 免责声明 / `requires_human_review` / `uncertain` 保留 / 无身份信息 的综合达标率 | | | | |
| 10 | 本地兜底率 | Tier 0+1 占全部推理调用的比例 | | | | |
| 11 | Tier 2 调用次数/任务 | 云端调用频次（成本代理指标） | | | | |
| 12 | P95 端到端延迟 | 单任务 P95 墙钟时间 | | | | |

> 不参与加权平均——必须在报告中单列并加粗。

## 4. 结果呈现（A5 产出）

1. **主表**：上表四臂逐项填数，标出 B 相对 A 的提升与 C 相对 B 的退化。
2. **差值表**：`Δ1 = B − A`（逐指标差值，符号随该指标的 `direction` 解释）、
   `Δ2 = FTR(C) − FTR(B)`（负向条件的净收益；**FTR 越低越好，故正值 = Not-for 段带来的净收益**）。
3. **逐用例附录**：40 条用例的预期 / 实际 / 是否命中，标注不一致项的失败模式。
4. **失败模式归类**：误触发 / 漏触发 / 结论错误 / 边界穿透 / 静默降级，各计频次。
5. **一句话结论**：用 `Δ2` 的数值直接回答「Not for 条件值多少分」。

## 5. 可复现性

```bash
# 各臂分别跑一遍，产出 results/{arm}.json
py -3.12 skills/evals/run_comparison.py --arm A --cases skills/*/evals/cases.jsonl --out skills/evals/results/A.json
py -3.12 skills/evals/run_comparison.py --arm B --cases skills/*/evals/cases.jsonl --out skills/evals/results/B.json
py -3.12 skills/evals/run_comparison.py --arm C --cases skills/*/evals/cases.jsonl --out skills/evals/results/C.json
# 汇总成主表
py -3.12 skills/evals/run_comparison.py --report skills/evals/results/*.json
```

- 结果 JSON 必须随仓库提交（可复现性证据）。
- 报告须写明模型版本、日期、运行次数。
- **不得只报最好一次**；三次结果全量留存。

## 6. 撰写口径（供 C3 征文与 C2 文档引用）

- 主结论必须是**定量**的：`带 skill 使负向误触发率从 X% 降到 Y%`。
- 明确声明本评测的边界：用例规模 40 条，是自建集而非公开基准，结论不外推。
- 明确声明未做 DGX Spark 实测，本地硬件为 RTX 5060 Laptop 8 GB。
