## Q2. Agent Skills 实操：怎么建、目录结构、SKILL.md、硬性要求与最佳实践

**这是全场信息密度最高的部分，且三位讲师反复交叉强调。以下全部为【原话】/【推断】混合，逐条标注。**

### 2.1 目录结构（硬事实）

【原话】
> 从文件结构看呢，一个 skill 呢可以非常的轻量，它就是由 skill 点 MD 和参考资料和脚本组成。（行 100，刘春辉）

【推断】即标准三件套：`SKILL.md` + 参考资料（references）+ 脚本（scripts）。

何坤补充了一个真实 skill 的内部构成【原话】：
> 第一我们要有一个 skill 的 Markdown 文件，其实是给 RM 看的使用说明书……然后呢下面还有 rehelper……那下面呢 superhero 的 helper，那其实业务逻辑调用，其实是调度 compui 的这个 API 的。然后最下边 workflow 呢，这个呢是一个工作流。（行 406）

### 2.2 SKILL.md 写法：description 是常驻成本，必须写清触发边界

【原话】（周旭，引用 NVIDIA 官方博客）
> 常驻的只有 description，大约 100 token 一个技能，所以没有人会全装 343 个技能。按需安装，加目录路由才是工程上的正确解。（行 238）

【原话】（何坤）
> 在千万要写清楚、写明白，在什么时候能够触发它，在什么范围内触发它。（行 400）

> 大家知道，其实我们的一个 agent 可能有几十、上百个skill，上千个skill，这都有可能。那如果你不写清楚了，你说这些 skill 每次如果都加载，那其实它是一个非常大的上下文量了。（行 403）

【原话】（周旭，触发关键词与**反向触发词**）
> 左边的代码是 NVIDIA 技能的 description 原文，触发关键词写进去，红色那两行是 native triggers，告诉 agent 什么时候**不要**触发。（行 238）

### 2.3 三条心法（刘春辉，唯一被明确命名为「心法」的方法论）

【原话】
> 我们在使用 Skill 的时候呢，我们有跟大家介绍这个三条心法，第一个叫**窄触发强路由**，就是我们尽量让这个 Skill 呢能够专注一件事情，就是即使说我们面向的是一个比较宽泛的需求……我们也可以把这个任务呢，拆成几个子的，几个skill，分布去调用。（行 187）

> 还有一个是我们的**前置问题**，一定要规定好这些 skill 呢，是到底是在我们执行这些 skill 的时候，我们需要做些什么？比如说刚才我去从一台机器上去登录到另一台机器上的时候，它实际上是需要您预装 SSH pass 的。（行 190）

> 还有一个**安全边界的内嵌**，就是我们一个 skill 里边有很多步骤，我们针对于某种步骤，如果做限制的时候，我们就要写在那个步骤里，而不是说我们已经一共四步，我们在最后才告诉他……而是说在第二步你不要干什么，你要干什么，就是有没有这种内嵌式的安全边界，要具体。（行 193）

### 2.4 自检查/自循环：skill 要能自我更新

【原话】
> 那一般来讲处理的时候，我们就在 skill 里边说，如果我纠正了你某些行为，你就要去更新你自己的skill。就是让他一个叫自检查的过程。随着您的使用……越多，您就不停的在补充，也可以利用这种自循环的方式进行。（行 190）

### 2.5 正/反向提示词（**两位讲师独立强调**）

【原话】（刘春辉）
> 所以呢，这个评测必须包含**负向用例**，有些任务的正确答案就是**不调用这个Skill**。如果大家呢准备自建这些Skill……也是要建议呢，要明确它解决哪些任务，以及不应该介入哪些业务，就是有正向提示词，应该也有反向提示词，然后再组织成组指令。（行 118）

【原话】（何坤）
> 就是不要，不只要有正向的提示词，也要有非常明确的反向的提示词，不要怎么着，不要怎么怎么怎么着，这些其实都是我们需要去注意的。（行 412）

### 2.6 硬红线：**不要直接改官方 skill**

【原话】（何坤，转述并强化刘春辉的观点）
> 其实春辉老师，他也提醒过了，我这里再再唠叨两句，再赘述一遍哈，**你不要去直接修改去官方的skill**，其实你就负责编配，去负责改内容，它原来千问其实就不再，就不认了哈。你就可以去自己去编配它哈，不用去改你原来的。（行 436）

### 2.7 从任务出发，不要从产品名出发

【原话】（何坤）
> 其实我们的理念呢，其实也是从任务出发，而不是从产品的名字出发哈。先说清楚要做一个skill，先设定这个部署、生产、训练、检索这些……你就要先说清楚，再写这个 description 这些东西。（行 355）

### 2.8 去重检查：skill 太多会导致「选择困难症」

【原话】（刘春辉）
> 我们会发现有些 skill 呢和有些 skill 它们之间的内容呢，是和功能性有一个重叠性。这种重叠性的会有可能就会造成我们基础模型叫**选择困难症**。同一，它的表现呢，就是我们同一个任务执行多次，每一次的结果呢，都有可能不一样。（行 109）

> 就是如果你之前的基模配置了一个skill，它跑起来很好，但是它由于呢，这个模型的更新，这个基模更新了，它已经具备了某些 skill 的能力了，这时候你还给它配相同的skill，它这就很有可能会造成我们 agent 那个**失智**。（行 115）

### 2.9 NVIDIA Verified Skills 五道工序（官方质量标准，可作为我们的对标）

【原话】
> 这里边的 verify 呢，它包含了五个部分，叫 cataloged、scanned、evaluated、signed 和 documented。（行 103）

> 那安全扫描呢……有 68 种漏洞模式，17 个类别，采用静态检查，并结合大语言模型呢，做意图与行为的语义分析。（行 109）

> Tier 3 的方法呢很简单，就是同一个 agent 在同一组任务里边，分别呢在不带 skill 或者是带 skill 的条件下呢运行，再比较结果。这样呢才能把模型本身就会做与 skill 带来的帮助呢做区分。（行 115）

【推断】Tier 3 的「有 skill / 无 skill 对照实验」是我们提交材料里最容易做、最能证明 skills 价值的证据形式，强烈建议做进我们的评测报告。

### 2.10 五维评测框架

【原话】
> 我们可不可以从五个维度去理解五个方向的检查哈？是否安全？结果呢？是否正确？是否在合适的时候呢？发现这个skill？任务呢？是否有效地完成？以及资源使用是否合理？（行 118）

## Q6. StepFun 模型用法

### 6.1 模型规格与能力（原话，均为官方数字）

### Q11.1 Skills 和 MCP 的本质区别？（**最有价值的一条**）

**问**（行 451）：
> 请问 Skills 和 MCP 到底有什么本质的区别？我们一般如何区分？我应该把某项技能做成 Skills 还是 MCP？

**答**（何坤，行 460–466，原话）：
> 其实这个问题，其实我觉得啊，其实就是一些**协议的一些形式问题**。打个比方啊，其实我们 MCP，以前我们叫 MCP 协议嘛，我们通常现在的一种形式都变成一种 **server 形式**，它可能需要连接某个网站，需要连接某个地方，更多的是**连接到某个地方**，去通过一些**外部的一些服务**，比如帮我们订票啦，帮我们去检索你的网，搜索网盘啦，帮我们去检索邮箱啦。anyway，这些呢更多是一种**服务器的性能的一些连接**。

> **skill 呢可能更广泛**，第一，skill 的意义在于，就是**它可以是你本地的**，可以是你一些**描述性的**，描述性它没有那种**非常强制的约束**，因为 MCP 需要非常强制的一个约束……那 skill 呢更多的是一种以，很多时候也可以以一种**自然语言**的表达方式。

【推断】判据：**连外部服务 → MCP；本地操作/流程知识/自然语言指令 → Skill。** 两者互补而非替代（周旭行 274 呼应：「三件事各司其职，谁也替代不了谁」）。
