> 适用于：第三届 NVIDIA DGX Spark 黑客松 · Agent Skills 开发挑战赛
> 约束：3 天工期 · 单机 RTX 5060 8 GB · 预算受限
> 版本：v1.0（2026-09-26）

---

## 0. 总监理职责边界

**做**：决策 · 派发 · 上下文注入 · 阶段裁决 · 升级/降级判断 · **唯一用户接口**

**不做**：读任何一行源代码 · 任何会污染上下文的直接作业

**边界说明**：总监理可以读「决策产物」（PRD、本文件、decision-log、验证报告），
但**不读源码、日志原文、模型输出原文**。一切需要通过阅读才能判断的事，一律派侦察兵。

**唯一用户接口**：所有 subagent 的报告回流到总监理，由总监理过滤、裁决、转述。
subagent 不得直接面向用户输出。用户的一切提问由总监理承接与澄清。

## 1. 角色编制

### 常设 4 员

| 代号 | 职责 | 建议 agent 类型 | 模型档 | 关键约束 |
|---|---|---|---|---|
| **R1 侦察兵** | 只读勘察：某物在哪、长什么样、依赖什么 | `Explore` | 轻 | **只回结论，不回代码** |
| **R2 执行者** | 写代码、跑命令、产出物证 | `general-purpose` | 中 | 必须附可复现命令 |
| **R3 验证者** | 独立复现，不信执行者自述 | `现实检验者` / `gsd-verifier` | 中 | **默认立场是「未达成」** |
| **R4 监察员** | 卡死检测，只报告不修 | `loop-operator` | 轻 | 只用 Bash，不读代码 |

### 按需专家（触发式，不常驻）

| 触发条件 | 调用 |
|---|---|
| 构建/环境失败 | `build-error-resolver` |
| 代码产出后 | `python-reviewer` |
| 涉及密钥、输入解析、网络调用 | `security-reviewer` |
| 需要对外演示数字 | `性能基准师` |
| 提交文档阶段 | `doc-updater` |
| 连续 3 次失败、需换思路攻坚 | 升级到重推理档 |

**编制原则**：常设角色保持最小。按需专家用完即弃，不保留上下文。

## 2. 通信协议（token efficiency 的核心）

### 2.1 报告契约（强制，所有 subagent）

```
STATUS:   DONE | PARTIAL | BLOCKED | FAILED
RESULT:   ≤10 行结论，禁止过程叙述
EVIDENCE: file:line 或 命令+输出节选，≤5 行
CHANGED:  新增/修改文件路径清单（无则写 none）
BLOCKERS: ≤3 条，每条一句话 + 已尝试过什么
NEXT:     ≤2 条建议
```

**硬上限 ~350 词**。派发时把此 schema 内联在任务里。

#### 两条硬要求（2026-09-28 新增）

**① `EVIDENCE` 必须能证伪 `RESULT`。**

写结论前先问一句：

> **「如果这条结论是错的，我这份证据会是什么样？」**

**答不上来，说明证据还没到。** 这条要的是**两者配对**，不是各自达标——
`RESULT` 写得再谨慎，配上一条证明不了它的 `EVIDENCE`，也只是把不确定包装成了已核实。

**判据（收报告的人一眼可查）**：把 `EVIDENCE` 单独拎出来看，**它能否推出 `RESULT`？**
不能 ⇒ 退回补充，不要「先记下结论，证据待补」。

> **为什么是问句不是纪律**：时间压力下，**问句能被回答，美德只能被遗忘。**

**② 能一分钟验的，不要写成待办——现在就验。**

**理由（有实例）**：2026-09-28，一个 agent 跑了一条 `git ls-remote`（走 HTTPS）失败，
据此写下「本机无网络」并挂成「待网络核验」的待办。
**危害不在结论错，在于「待办」这个形式让它获得了免于被质疑的外观**——
后来的人看到的是「这件事被处理过了」，于是不再怀疑那个前提本身。

> **实例出处（可 grep）**：`docs/SUBMISSION-CHECKLIST.md` §一末「一条工具链教训」。
> 更正后的准确事实：`git` 走显式 https URL 会被一条死代理挡住，走 `origin`（SSH）正常——
> **推送通路一直是好的**。

⇒ **写下任何「待处理 / 待核验 / 已记录」之前，先问：这个结论我是验过，还是只跑了一次、扫了一眼、推出来的？**
**没验的，条目里必须带「未验证」三个字，并写清「怎么验、一分钟能不能验」。**

> 相关：`docs/agents/fact-single-source.md`（现状断言的单一来源）、
> `CONTEXT.md` 开头的 `[团队自定]` 标签。

### 2.2 八条效率机制

| # | 机制 | 说明 |
|---|---|---|
| 1 | **指针注入** | 总监理只给文件路径 + 任务，不给文件内容 |
| 2 | **零原文回传** | 禁止回传文件全文；只给 file:line + ≤5 行证据 |
| 3 | **决策日志落盘** | 落 `docs/agents/decision-log.md`，agent 自读，总监理不复述 |
| 4 | **并行批处理** | 独立任务同批派发，不等串行 |
| 5 | **升级阶梯** | 先轻档 agent，失败才上重档 |
| 6 | **两次即停** | 同一错误出现 2 次 → 立即上报总监理，禁止第 3 次重试 |
| 7 | **物证优先** | 交付物是文件/命令输出，不是文字描述 |
| 8 | **读取预算** | 每次派发声明「最多读 N 个文件」，超出即上报 |

### 2.3 反模式（明令禁止）

- ❌ subagent 回传大段代码或日志
- ❌ 总监理亲自 grep / read 源码
- ❌ 同一 agent 反复重试同一思路
- ❌ 无成功判据就派发任务

## 3. 派发模板

每次派发必须含齐五项，缺一不可：

```
1. 任务      ：一句话可验证的目标
2. 指针      ：需要读的文件路径（不是内容）
3. 成功判据  ：可执行命令 + 期望输出
4. 观察点    ：完成过程中「应该变化」的文件/指标（供监察员用）
5. 预算      ：读取上限 + 预期完成窗口 + 失败上限(默认2)
```

**无成功判据不得派发**——这是防止「看起来完成了」的第一道闸。

## 4. 工作流

### 4.1 单任务闭环

```
总监理派发
   ↓
R2 执行者 ────────┐
   ↓              │ 超窗口/停滞
  报告            ↓
   ↓         R4 监察员 → 报总监理 → 裁决
R3 验证者 独立复现          ↓
   ↓              继续 / 换法 / 砍范围 / 放弃
  裁决：过 / 回炉 / 降级
   ↓
写入 decision-log → 下一任务
```

### 4.2 阶段闸门

每个阶段必须**验证者独立复现**才能过闸。

| 阶段 | 交付 | 过闸判据（可执行） |
|---|---|---|
| **P0 环境** | 可用 CUDA 环境 | `torch.cuda.is_available()` 为 True；sm_120 上 bf16 矩阵乘成功；显存读数正确 |
| **P1 感知层** | Tier 0 检测 | 样例视频输出带框结果；帧率与显存占用有实测数字 |
| **P2 判读层** | Tier 1 本地 VLM | 对裁剪图输出分类结论；有准确率基线 |
| **P3 路由+Skill** | 三层路由 + SKILL.md | 分级切换日志可查；Agent 经 Skill 驱动完整流程 |
| **P4 交付** | 视频/文档/部署说明 | 仓库可被第三方克隆复现；材料清单齐全 |

## 5. 卡死监察协议（R4）

### 5.1 触发条件

- 超出声明完成窗口 50%
- 同一错误出现 2 次
- 观察点文件 mtime 停滞 > 10 min
- 连续 2 次巡检关键指标无增长（如测试通过数）
- agent 重复相同 tool call

### 5.2 检查手段（仅 Bash，不读代码）

```bash
git status --short          # 有无新产出
ls -lt <观察点目录> | head  # mtime 是否在动
# 进程存活 / 日志尾部 / 指标计数
```

### 5.3 输出格式（≤5 行）

```
STUCK:    yes | no | unsure
SIGNAL:   观察到的事实（mtime/错误/计数）
LIKELY:   最可能的原因（一句话，带不确定性标注）
OPTIONS:  继续 / 换法 / 砍范围 / 放弃 —— 各附一句代价
```

**R4 绝不自己修**，只报给总监理。

## 6. 升级与降级（对齐 harness-blueprint）

```
RUNNING → 成功 → VERIFYING → DONE
             ↓ 判据不通过
          RETRYING (≤2)  ← 附失败上下文重派
             ↓ 仍失败
        FALLING_BACK
             ├─ 换更强模型重试
             ├─ 降级：砍掉非核心需求，保核心通路
             └─ 上报总监理决断
```

**团队自定原则（不是赛事规定）**：**一个能跑的小东西 > 一个跑不通的大东西**。
降级默认优先于死磕。

> 这是我们自己的取舍，**不出自任何官方材料**。原句写作「**黑客松特别条款**：完整性占 30%」，
> 已于 2026-09-28 更正 —— 见本节末的更正记录。

**与之相关、且确有出处的事实**（`[官方PPT + 训练营逐字稿，双源一致]`，见 `CONTEXT.md` §3）：

| 维度 | 权重 | 官方原话要点 |
|---|---|---|
| 项目实用性、行业落地价值与技术创新性 | **25** | 技术实现、架构与方案具备创新性，突破传统思路并解决技术痛点 |
| 智能体与模型优化技术深度 | **25** | 多智能体协同、模型调优深度、**skills 的设计和 agent 融合** |
| **项目完整性** | **20** | 「需要您的作品**功能完整、运行稳定，前端后端都有，文档详实，实现逻辑清晰**，能够顺利去完成你 demo 的演示」 |
| 平台适配性 | **15** | 充分发挥 DGX Spark 全栈能力、NVIDIA 技术栈与**阶跃星辰模型的使用** |
| 演示效果 | **10** | 「你的**视频要演示流畅**，更加直观的让我们看到你作品的价值」 |
| 赛事征文 | **5** | 「虽然这 5 分哈，其实它就是很多情况下**能拉开差距**的一个部分」 |

合计 `25+25+20+15+10+5 = 100`。

> 🔴 **更正记录（2026-09-28）**
>
> 本条原文为：**「黑客松特别条款：完整性占 30%，一个能跑的小东西 > 一个跑不通的大东西。」**
>
> **两处错误**：
> 1. **「黑客松特别条款」这个名目不存在于任何原始材料**——它是一句团队自定判断，
>    被加上了引号语气的名目，**看起来像一条官方规则**。
> 2. **30% 是错的**。官方为 **20**；原表 `25+25+30+15+10+5 = 110`，**数学上不成立**。
>    该错误在 `CONTEXT.md:157`、`decision-log.md:79`、`PRD.md:254` 均已更正，
>    **唯独漏了本条**。
>
> **为什么漏掉的是这一条**：其它几处的错误以「评分表」形式出现，扫描按数字找得着；
> 而这一条被包装成一条「条款」，**数字藏在散文里，逃过了按表格式的核对。**
>
> **教训（比这次更正本身重要）**：**给一句自己的判断加上一个像出处的名目，
> 会让它免于被核查——包括免于被我们自己核查。** 团队自定原则就写「团队自定」，
> 不要借官方的语气。今后凡在文档里看到「条款 / 规定 / 要求」这类名目，
> 一律要求给出处；**查不到出处的，改写为「团队自定」或删除。**
