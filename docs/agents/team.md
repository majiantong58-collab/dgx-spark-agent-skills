# Agent Team & Workflow — 总监理制

> 适用于：第三届 NVIDIA DGX Spark 黑客松 · Agent Skills 开发挑战赛
> 约束：3 天工期 · 单机 RTX 5060 8 GB · 预算受限
> 版本：v1.0（2026-09-26）

---

## 0. 总监理职责边界

**做**：决策 · 派发 · 上下文注入 · 阶段裁决 · 升级/降级判断 · **唯一用户接口**

**不做**：读任何一行源代码 · 任何会污染上下文的直接作业

**边界说明**：总监理可以读「决策产物」（PRD、本文件、decision-log、验证报告），
但**不读源码、日志原文、模型输出原文**。一切需要通过阅读才能判断的事，一律派侦察兵。

**唯一用户接口**：所有 subagent 的报告回流到总监理，由总监理过滤、裁决、转述。
subagent 不得直接面向用户输出。用户的一切提问由总监理承接与澄清。

## 1. 角色编制

### 常设 4 员

| 代号 | 职责 | 建议 agent 类型 | 模型档 | 关键约束 |
|---|---|---|---|---|
| **R1 侦察兵** | 只读勘察：某物在哪、长什么样、依赖什么 | `Explore` | 轻 | **只回结论，不回代码** |
| **R2 执行者** | 写代码、跑命令、产出物证 | `general-purpose` | 中 | 必须附可复现命令 |
| **R3 验证者** | 独立复现，不信执行者自述 | `现实检验者` / `gsd-verifier` | 中 | **默认立场是「未达成」** |
| **R4 监察员** | 卡死检测，只报告不修 | `loop-operator` | 轻 | 只用 Bash，不读代码 |

### 按需专家（触发式，不常驻）

| 触发条件 | 调用 |
|---|---|
| 构建/环境失败 | `build-error-resolver` |
| 代码产出后 | `python-reviewer` |
| 涉及密钥、输入解析、网络调用 | `security-reviewer` |
| 需要对外演示数字 | `性能基准师` |
| 提交文档阶段 | `doc-updater` |
| 连续 3 次失败、需换思路攻坚 | 升级到重推理档 |

**编制原则**：常设角色保持最小。按需专家用完即弃，不保留上下文。

## 2. 通信协议（token efficiency 的核心）

### 2.1 报告契约（强制，所有 subagent）

```
STATUS:   DONE | PARTIAL | BLOCKED | FAILED
RESULT:   ≤10 行结论，禁止过程叙述
EVIDENCE: file:line 或 命令+输出节选，≤5 行
CHANGED:  新增/修改文件路径清单（无则写 none）
BLOCKERS: ≤3 条，每条一句话 + 已尝试过什么
NEXT:     ≤2 条建议
```

**硬上限 ~350 词**。派发时把此 schema 内联在任务里。

### 2.2 八条效率机制

| # | 机制 | 说明 |
|---|---|---|
| 1 | **指针注入** | 总监理只给文件路径 + 任务，不给文件内容 |
| 2 | **零原文回传** | 禁止回传文件全文；只给 file:line + ≤5 行证据 |
| 3 | **决策日志落盘** | 落 `docs/agents/decision-log.md`，agent 自读，总监理不复述 |
| 4 | **并行批处理** | 独立任务同批派发，不等串行 |
| 5 | **升级阶梯** | 先轻档 agent，失败才上重档 |
| 6 | **两次即停** | 同一错误出现 2 次 → 立即上报总监理，禁止第 3 次重试 |
| 7 | **物证优先** | 交付物是文件/命令输出，不是文字描述 |
| 8 | **读取预算** | 每次派发声明「最多读 N 个文件」，超出即上报 |

### 2.3 反模式（明令禁止）

- ❌ subagent 回传大段代码或日志
- ❌ 总监理亲自 grep / read 源码
- ❌ 同一 agent 反复重试同一思路
- ❌ 无成功判据就派发任务

## 3. 派发模板

每次派发必须含齐五项，缺一不可：

```
1. 任务      ：一句话可验证的目标
2. 指针      ：需要读的文件路径（不是内容）
3. 成功判据  ：可执行命令 + 期望输出
4. 观察点    ：完成过程中「应该变化」的文件/指标（供监察员用）
5. 预算      ：读取上限 + 预期完成窗口 + 失败上限(默认2)
```

**无成功判据不得派发**——这是防止「看起来完成了」的第一道闸。

## 4. 工作流

### 4.1 单任务闭环

```
总监理派发
   ↓
R2 执行者 ────────┐
   ↓              │ 超窗口/停滞
  报告            ↓
   ↓         R4 监察员 → 报总监理 → 裁决
R3 验证者 独立复现          ↓
   ↓              继续 / 换法 / 砍范围 / 放弃
  裁决：过 / 回炉 / 降级
   ↓
写入 decision-log → 下一任务
```

### 4.2 阶段闸门

每个阶段必须**验证者独立复现**才能过闸。

| 阶段 | 交付 | 过闸判据（可执行） |
|---|---|---|
| **P0 环境** | 可用 CUDA 环境 | `torch.cuda.is_available()` 为 True；sm_120 上 bf16 矩阵乘成功；显存读数正确 |
| **P1 感知层** | Tier 0 检测 | 样例视频输出带框结果；帧率与显存占用有实测数字 |
| **P2 判读层** | Tier 1 本地 VLM | 对裁剪图输出分类结论；有准确率基线 |
| **P3 路由+Skill** | 三层路由 + SKILL.md | 分级切换日志可查；Agent 经 Skill 驱动完整流程 |
| **P4 交付** | 视频/文档/部署说明 | 仓库可被第三方克隆复现；材料清单齐全 |

### 4.3 时间映射

| 时段 | 阶段 |
|---|---|
| D0 今晚 9/26 | P0 |
| D1 9/27 | P1 → P2 |
| D2 9/28 | P3 |
| D3 9/29 上午 | P4 |
| D3 9/29 下午 | 缓冲 + 提交 |

## 5. 卡死监察协议（R4）

### 5.1 触发条件

- 超出声明完成窗口 50%
- 同一错误出现 2 次
- 观察点文件 mtime 停滞 > 10 min
- 连续 2 次巡检关键指标无增长（如测试通过数）
- agent 重复相同 tool call

### 5.2 检查手段（仅 Bash，不读代码）

```bash
git status --short          # 有无新产出
ls -lt <观察点目录> | head  # mtime 是否在动
# 进程存活 / 日志尾部 / 指标计数
```

### 5.3 输出格式（≤5 行）

```
STUCK:    yes | no | unsure
SIGNAL:   观察到的事实（mtime/错误/计数）
LIKELY:   最可能的原因（一句话，带不确定性标注）
OPTIONS:  继续 / 换法 / 砍范围 / 放弃 —— 各附一句代价
```

**R4 绝不自己修**，只报给总监理。

## 6. 升级与降级（对齐 harness-blueprint）

```
RUNNING → 成功 → VERIFYING → DONE
             ↓ 判据不通过
          RETRYING (≤2)  ← 附失败上下文重派
             ↓ 仍失败
        FALLING_BACK
             ├─ 换更强模型重试
             ├─ 降级：砍掉非核心需求，保核心通路
             └─ 上报总监理决断
```

**黑客松特别条款**：完整性占 30%，**一个能跑的小东西 > 一个跑不通的大东西**。
降级默认优先于死磕。

## 7. 成本控制

| 档位 | 用于 | 说明 |
|---|---|---|
| 轻 | R1 侦察兵、R4 监察员 | 高频、低判断量 |
| 中 | R2 执行者、R3 验证者 | 主力 |
| 重 | 攻坚、架构级决策 | 仅升级时启用 |

**估算**：全流程约 20–35 次 agent 调用。监察员巡检为低成本作业。
**真实成本以实测为准**，首阶段结束后校准。
